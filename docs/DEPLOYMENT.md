# Deployment, domain and updates

## Recommended: the included GitHub Actions workflow

Follow the seven steps in the root README. Use a private repository and add the two Cloudflare credentials through GitHub Secrets. GitHub stores the project; Cloudflare Workers hosts the application and runs the enquiry API. D1 stores enquiry records and R2 stores attachments.

The workflow provisions resources by exact name. It does not purchase services, change the current domain, modify the ChatGPT Site or copy any existing business records. It publishes a workers.dev endpoint in your Cloudflare account.

The setup script writes actual identifiers into `wrangler.generated.json`. This file is ignored by Git. The compiled configuration is generated by the Cloudflare Vite plugin at `dist/server/wrangler.json`. The deploy script uses that compiled configuration with the matching `dist/client` assets.

Only run one automatic deployment integration for the same Worker. Use either the included GitHub workflow or Workers Builds below, to avoid duplicate releases.

## Alternative: Cloudflare Workers Builds connected to GitHub

This is useful if you already connected the repository in Cloudflare.

1. In Cloudflare, open **Workers & Pages → Create application** and connect/select the GitHub repository. Choose a Worker application.
2. Use these build settings:

   | Setting | Value |
   | --- | --- |
   | Worker name | `ran-engineers` |
   | Root directory | Repository root, where `package.json` is located |
   | Production branch | `main`, or your actual default branch |
   | Build command | `npm run build:cloudflare` |
   | Deploy command | `npm run deploy:prepared` |
   | Node version | `24` |

3. Add **build** secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` with the permissions listed in README. Set `NODE_VERSION=24` if the build image needs an explicit override. These scripts access D1/R2 during setup; the dashboard's default deploy token may not include D1 permissions, so use the scoped token described in README.
4. R2 must already be enabled. Set build variable `VITE_SITE_URL=https://www.ranengineers.com` (also the code default).
5. Keep branch/PR previews disabled for this production integration unless separate resource names are configured. Preview builds must not unintentionally reuse the production enquiry database.
6. Trigger the build. The platform installs the dependencies, then runs the configured commands. Check its workers.dev URL.

If Cloudflare overrides the Worker name because you chose a different dashboard name, set `RAN_WORKER_NAME` to that same name so the setup, build and deployment agree.

## Local command-line deployment

Install Node 24 and run `npm ci`. Set both Cloudflare credentials in the shell's environment without committing them to Git, then run:

```sh
npm run deploy:cloudflare
```

This uses the same scripts as GitHub. To build with the actual resources without publishing:

```sh
npm run build:cloudflare
```

Local development is separate:

```sh
npm run db:migrate:local
npm run dev
```

The local database and bucket are emulated. Production credentials are not required for ordinary local development or local checks.

## Connect www.ranengineers.com after verification

1. Confirm the new workers.dev deployment serves the expected pages and images.
2. Confirm a labelled test enquiry produces a receipt and persists in the correct D1 database. Confirm an attached test file exists in the private R2 bucket.
3. Finish the existing-data migration in `DATA-MIGRATION.md`, including any final enquiries received while the old site remained active.
4. Record the current website's domain/DNS settings so the cutover can be reversed if needed. Keep the current hosting available during the transition.
5. In the target Cloudflare Worker, open **Settings → Domains & Routes → Add → Custom Domain** and add `www.ranengineers.com` when you are ready to move traffic. The domain must belong to the correct active Cloudflare zone. Resolve any existing DNS/domain conflict at this point, not before the new site is ready.
6. Verify HTTPS and test the form on the actual company domain. The API uses same-origin requests, so `/api/enquiry-token` and `/api/enquiries` must reach the same Worker as the pages.
7. Configure the apex `ranengineers.com` separately if you use it, preferably redirecting it to the canonical `www` domain.

The package intentionally contains no domain routes. The `VITE_SITE_URL` value controls canonical metadata and sitemap URLs; it does not connect or transfer the domain.

## Updates

Edit source files and commit to GitHub. Run the deployment workflow again, or set repository variable `CLOUDFLARE_AUTO_DEPLOY=true` to deploy pushes to main automatically. Keep resource names and Cloudflare account consistent. Wrangler records applied migrations and applies only pending files.

Do not edit compiled files in `dist`. Build them from source. Do not commit `node_modules`, `dist`, `wrangler.generated.json`, credentials, database dumps or local runtime storage.

## Reviewing enquiries

In Cloudflare D1, open `ran-engineers-enquiries` and inspect the `enquiries` table. For example, this read-only SQL lists recent receipt details:

```sql
SELECT reference, datetime(received_at / 1000, 'unixepoch') AS received_utc,
       full_name, company, phone, email, requirement, message, attachment_key
FROM enquiries
ORDER BY received_at DESC
LIMIT 100;
```

Use the returned `attachment_key` to find the object in the private `ran-engineers-enquiry-attachments` bucket. There is no public enquiry list or attachment download API, and this release does not add email notifications or an admin dashboard.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| Actions workflow is missing | `.github/workflows/deploy-cloudflare.yml` must be uploaded on the repository's default branch. |
| Run is skipped after an upload | First run is manual. Open Actions and choose Run workflow, or enable `CLOUDFLARE_AUTO_DEPLOY=true` for future pushes to main. |
| Account/token missing | Check exact GitHub secret names. Use repository Secrets, not ordinary source files. |
| Cloudflare authorization error | Account ID and token must belong to the same account; include Workers Scripts, D1, R2 and Account Settings permissions. |
| R2 setup fails | Activate R2 in that account and confirm Workers R2 Storage Edit permission. Setup reports the API error and stops. |
| Existing schema without migration history | Follow `DATA-MIGRATION.md`. Never delete existing enquiry tables to silence the error. |
| Wrong build folder | Ensure `package.json` is in the configured root, not one extra extracted folder below it. |
| Node or native binary error | Use Node 24 and a clean `npm ci`. Keep the supplied lockfile. Do not upload node_modules from another operating system. |
| Enquiry returns 503 | Check `DB` and `BUCKET` bindings, migrations, the chosen account and the Worker logs. |
| Missing photograph | Upload the full `public` directory, preserving filenames and case. The steel-plant representative photo also uses its existing external image provider with a local fallback. |
| Existing domain still shows old site | A workers.dev deployment does not move the domain. Complete the tested custom-domain cutover. |
